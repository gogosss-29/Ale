CONCEPTO 1 ●

¿Qué es Git?

Un sistema de control de versiones.

Una herramienta que instalas en tu computadora y que rastrea cada cambio que haces en tus archivos.

Es local, funciona offline, y crea una línea de tiempo de tu proyecto que puedes recorrer hacia atrás.

Lo creó Linus Torvalds en 2005, el mismo de Linux.

💾

El motor que vive en tu laptop

Sin internet. Sin cuenta. Sin nube.
Solo tú y tus archivos.

Slide 2 · ¿Qué es Git? 0:01 – 0:02

  • Analogía: Git es como Ctrl+Z infinito, pero para todo tu proyecto y con etiquetas.
  • Insistir: Git no necesita internet. Es 100% local. Mucha gente confunde esto.
  • Anécdota: cuántas veces has perdido código por no tener versiones — esto lo resuelve.
0:00 – 0:05 · Intro

CONCEPTO 2 ●

¿Qué es GitHub?

Una plataforma online para hospedar repos.

Es donde subes tus proyectos de Git para tenerlos respaldados y colaborar con otros.

Además trae herramientas sociales y de equipo: Pull Requests, Issues, Actions, revisiones de código, releases...

Empresa de Microsoft desde 2018. ~100M de desarrolladores.

☁️

El nodo en la nube

Donde el equipo se encuentra.
Donde vive la versión "oficial".

Slide 3 · ¿Qué es GitHub? 0:02 – 0:03

  • Mencionar competidores: GitLab, Bitbucket, Codeberg — pero el estándar de la industria es GitHub.
  • "Es como Instagram, pero de código": perfil público, seguidores, contribuciones visibles.
  • Aclarar: GitHub no es Git. Puedes usar Git sin GitHub. Pero GitHub sin Git no existe.

PASO 2 ●

Configuración inicial

Solo se hace una vez por máquina. Esto firma tus commits con tu nombre y correo.

# Tu identidad — usa el mismo email que en GitHub
$ git config --global user.name "Carlos Domínguez"
$ git config --global user.email "carlos@ejemplo.com"

# Rama por defecto al crear repos nuevos
$ git config --global init.defaultBranch main

# Tu editor preferido para los mensajes largos
$ git config --global core.editor "code --wait"

# Ver toda la config actual
$ git config --list

↑ el flag --global = aplica a todos tus repos en esta máquina

Slide 6 · Config inicial 0:08 – 0:11

EN VIVO ●

Tu primer repo en 30 segundos

# 1. Entra a una carpeta cualquiera
$ cd mi-proyecto

# 2. Inicializa Git ahí (crea una carpeta oculta .git)
$ git init
Initialized empty Git repository in /Users/carlos/mi-proyecto/.git/

# 3. ¿Qué tengo? Te muestra el estado actual
$ git status

# 4. Pongo archivos en staging (el "." = todos)
$ git add .

# 5. Hago la foto con un mensaje descriptivo
$ git commit -m "chore: initial commit"
[main (root-commit) a1b2c3d] chore: initial commit
 3 files changed, 42 insertions(+)

↑ ¡felicidades! ya tienes un repo con historia ↑

  • Truco 2: git commit -am "msg" hace add+commit en uno (solo de archivos ya rastreados).

UNIVERSOS PARALELOS ●

¿Qué es una rama?

Una línea paralela de desarrollo. Te separas de main, experimentas sin miedo, y cuando funciona lo traes de vuelta.

Sirve para:

  • Probar una idea sin romper lo que funciona
  • Trabajar en una feature mientras otro arregla un bug
  • Hacer code reviews antes de mezclar

Regla: jamás programes directo en main

main
feat/login
fix/header

↑ tres líneas de tiempo, mismo proyecto

Slide 13 · Concepto de rama 0:25 – 0:27

  • Analogía: como un "Guarda partida" de videojuego antes del jefe final. Si mueres, vuelves al save.
  • Insistir: las ramas son baratas en Git. No son carpetas duplicadas — son punteros. Crear una toma 0 ms.
  • Trivia: en GitHub la rama default ahora es main, antes era master. Cambio histórico de 2020.
0:25 – 0:35 · Ramas + GitHub

COMANDOS ●

Trabajar con ramas

# Ver todas las ramas (la actual marcada con *)
$ git branch
* main
  feat/login

# Crear una rama nueva Y cambiarte a ella
$ git switch -c feat/dashboard
# equivalente legacy: git checkout -b feat/dashboard

# Cambiarte a una rama existente
$ git switch main

# Mezclar feat/dashboard EN main
$ git switch main
$ git merge feat/dashboard

# Borrar una rama cuando ya no la necesitas
$ git branch -d feat/dashboard

Workflow típico: switch → editar → add → commit → switch main → merge

Slide 14 · Comandos de ramas 0:27 – 0:29

  • git switch es nuevo (Git 2.23+). git checkout sigue funcionando, lo verán en tutoriales viejos.
  • Diferencia: checkout hace muchas cosas (ramas, archivos, commits). switch es solo para ramas → más seguro.
  • Demo: crear rama, hacer un cambio, mergear de vuelta a main. Que la audiencia vea el flujo.

DE LOCAL A LA NUBE ●

Conectar con GitHub

3 pasos para subir tu repo

  1. Crea el repo en GitHub: botón New repository → nombre → sin README (lo tienes ya local).
  2. Copia la URL que te muestra (HTTPS o SSH).
  3. Apunta tu repo local a esa URL y empuja.

↓ los comandos exactos

# Apunta tu repo local al remoto
$ git remote add origin \
    https://github.com/tu-user/mi-repo.git

# Verifica
$ git remote -v
origin  https://github.com/.../mi-repo.git (fetch)
origin  https://github.com/.../mi-repo.git (push)

# Sube y crea la rama main en remoto
$ git push -u origin main
Branch 'main' set up to track 'origin/main'.

El -u = solo la primera vez. Después basta git push

Slide 15 · Conectar con GitHub 0:29 – 0:31

  • origin es solo el nombre por convención del remoto principal. Podrías llamarle upstream, github... pero el mundo usa origin.
  • Recomendar HTTPS al principio (más fácil), SSH cuando ya tengan llaves configuradas. Token de acceso personal (PAT) reemplaza la contraseña.
  • Demo en GitHub: enseñar el botón "New repository" y la página de instrucciones que aparece.

EL CORAZÓN DE LA COLABORACIÓN ●

¿Qué es un Pull Request?

Una solicitud formal para que tus cambios en una rama se mezclen a main (u otra rama base).

Es donde el equipo:

  • Revisa tu código antes de mergear
  • Comenta sugerencias línea por línea
  • Aprueba o pide cambios
  • Discute decisiones técnicas con contexto

PR = el momento social de Git

Anatomía de un PR

  • Título: feat(auth): add Google OAuth
  • Descripción: qué, por qué, cómo probarlo
  • Base ← Compare: main ← feat/oauth
  • Reviewers: 1-2 personas del equipo
  • Labels: bug enhancement
  • Checks: ✓ CI passing
  • Conversation: hilo de revisión

Slide 19 · Anatomía PR 0:38 – 0:40

  • Demo en vivo: abrir un PR cualquiera en GitHub (incluso un PR público famoso, p.ej. en facebook/react) y recorrer las pestañas: Conversation, Commits, Checks, Files changed.
  • Insistir: una buena descripción de PR ahorra horas. Plantilla: ¿qué hace? · ¿por qué? · ¿cómo se prueba?
  • Pregunta: "¿Cuántos commits debería tener un PR?" → idealmente 1-5. Si tiene 30, probablemente debería ser varios PRs.

EL ARTE DE REVISAR ●

Code Review

💬 Comment

Solo opinión, no bloquea. "¿Has pensado en X?"

✅ Approve

Te gusta como está. Listo para mergear (si CI verde).

🚫 Request changes

Bloquea el merge hasta que cambien algo. Úsalo con cuidado.

Reviewer = empatía + criterio

  • Critica el código, no a la persona
  • Pregunta antes de afirmar
  • Sugiere alternativas concretas
  • Aprueba si está "bien", no si está "perfecto"

Autor del PR = humildad + claridad

  • Responde cada comentario
  • Si no aplicas un cambio, di por qué
  • Re-pide review tras cambios grandes
  • Agradece (no es opcional)

Slide 22 · Code review 0:44 – 0:45

  • "Request changes" se reserva para problemas reales: bug, seguridad, romper convención. NO para "yo lo escribiría diferente".
  • Regla práctica: si el PR lleva >48h sin review, el autor puede dar un toque en Slack/chat — no es ser pesado, es destrabar.
  • Si eres reviewer y no sabes algo, di "no lo sé, ¿podrías explicarme?" — es mejor que aprobar a ciegas.

CUANDO GIT NO PUEDE DECIDIR ●

Conflictos de merge

Ocurren cuando dos personas modifican la misma línea del mismo archivo en ramas distintas.

Git no se atreve a elegir por ti. Marca el archivo, lo deja en un estado "conflict" y te pide ayuda.

No es un error.
Es una pregunta.

Así se ve en el archivo:

function saludar() {
<<<<<<< HEAD
return "Hola mundo";
=======
return "Hello world";
>>>>>>> feat/i18n
}

↑ HEAD = tu versión actual
↓ feat/i18n = la que vienes a mezclar

Slide 23 · Conflictos qué son 0:45 – 0:48

  • Despresurizar: a TODOS les pasa. No es "haberlo hecho mal".
  • Ocurren más cuando alguien hace cambios masivos sin actualizar su rama → moraleja: git pull origin main diario en tu rama feature.
  • Si la audiencia ya tuvo uno: pedirles que cuenten cómo lo resolvieron.
0:45 – 0:55 · Conflictos + Buenas prácticas

PASO A PASO ●

Resolver un conflicto

1

Abrir el archivo en conflicto

VSCode lo destaca con colores y botones "Accept Current / Incoming / Both".

2

Decidir qué versión queda

O combinar ambas. Borra los marcadores <<< === >>>.

3

Guardar y marcar como resuelto

git add archivo.js

4

Cerrar el merge

git commit (Git ya tiene un mensaje preparado)

Comandos útiles

# ¿qué archivos están en conflicto?
$ git status

# si te arrepientes, abortas todo
$ git merge --abort

VSCode + GitLens
= conflictos sin sufrir

Slide 24 · Resolver conflicto 0:48 – 0:50

  • VSCode tiene UI brutal para conflictos: "Accept Current", "Accept Incoming", "Accept Both", "Compare". Recomendar abrir un archivo conflict y mostrar.
  • Si pierdes el norte: git merge --abort deshace TODO y vuelves al estado antes del merge.
  • Demo opcional si hay tiempo: provocar un conflicto en un repo de prueba en vivo.

LAS 5 REGLAS QUE TE SALVAN ●

Buenas prácticas

1

Commits pequeños y frecuentes

Mejor 10 commits enfocados que 1 commit gigante. Cada commit = una idea.

2

Mensajes claros con convención

Sigue Conventional Commits: feat:, fix:, chore:, docs:.

No trabajes en main

Siempre una rama por tarea. main debería estar siempre desplegable.

4

.gitignore desde el día 1

Antes del primer commit. Especialmente .env y secretos.

5

git pull antes de empezar

Trae lo último cada mañana. Evita conflictos absurdos.

que un solo cambio gigante

EJEMPLO REAL · ATS · .github/workflows/ci.yml ●

Bonus: GitHub Actions

GitHub puede correr tareas automáticas en cada push o PR: lint, tests, deploy... Se configura con un archivo YAML.

name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: 20}
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run build

¿Qué hace este workflow?

  • Se dispara en cada push a main y en cada PR
  • Corre en una VM de Ubuntu
  • Instala deps, hace lint + typecheck + build
  • Si algo falla → bloquea el merge del PR

Tu PR no se mergea hasta que el robot diga ✓

Slide 26 · GitHub Actions 0:53 – 0:55

  • Actions son gratis hasta cierto límite para repos públicos. En privados también hay free tier generoso.
  • Hay miles de actions hechas: marketplace.github.com/actions. No reinventes la rueda.
